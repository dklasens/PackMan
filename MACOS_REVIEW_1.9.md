**PackMan macOS 1.9 release review — 5 September 2026**

Recommendation: bring the three main Windows 1.9 features to Mac—package details and recovery, persistent history, and selective cache previews—alongside fixes to verification, self-update replacement, scan counts, and App Store handoff. Add Homebrew scan deduplication and tool-cache invalidation as practical optimisations. A small source-setup improvement is more useful for this release than a scheduler or a large set of new package managers.

This is a review and proposed scope. Production code has not been changed. Evidence comes from the current Swift sources, Windows implementation and tests, `IMPLEMENTATION_1.9.md`, the previous platform reviews, release configuration, and linked upstream documentation. The older `MACOS_REVIEW.md` describes many issues already fixed; it should not be treated as the current backlog.

**Current baseline and release identity**

Mac already has concurrent source scans with incremental results, partial-result warnings, cancellation, a single shared window model, checkbox selection, search, semantic/natural sorting, ignored updates, source health and executable overrides, cached tool discovery, npm/Node pairing, exact npm/pip/.NET target arguments, npm script handling, pip dependency checks, batched verification, cache commands, and checksum-verified self-update downloads. Preserve these investments.

Version metadata is inconsistent across local build paths: `make-app.sh:24` and `project.yml:12` default to 1.8.2, the Xcode project also declares 1.8.2, while `AppViewModel.swift:913` falls back to 1.8.0. The README and `.github/release-notes/v1.9.md` describe an existing Mac build repackaged as 1.9. CI passes the tag into `make-app.sh`, which already verifies the resulting bundle version and build number.

Treat “Mac 1.9” as the feature scope until distribution identity is settled. If the documented 1.9 Mac build has already reached users, ship these features under a newer version, such as 1.9.1: the updater only offers strictly newer versions and would not offer replacement 1.9 assets to a 1.9 installation. This review could not independently fetch the public release page or inspect a downloaded artifact. Keep published tags immutable, consolidate build defaults, and assert both architectures rather than merely printing `lipo -info`.

**Correctness fixes to include before release**

1. **Verify installed state, without inventing versions.** `PackageSource.swift:189` implements verification by scanning for outdated packages; absence becomes `.satisfied(installedVersion: request.targetVersion)`. Homebrew, pip, pipx, and .NET inherit this. A removed package, excluded package, changed feed, or parser failure can therefore look successfully installed. `MasSource.swift:108` additionally ignores scan issues when doing the same inference. npm already reads installed inventory, although one missing npm package currently throws away the whole verification batch. Return per-package observed, still-outdated, missing, and inconclusive outcomes with evidence. Use installed inventory from the selected manager/environment; keep discovery/network failures separate. A request for 2.0 with observed 2.1 must retain 2.1 and use source-appropriate satisfaction rules. Temporary checks reproduced pip's invented version and App Store verification succeeding despite a network warning.

2. **Reject unrecognised scan formats.** `DotnetToolListParser.parse` (`DotnetSource.swift:193`) skips everything until an English table header and returns no issues when no header appears. A temporary check confirmed that unfamiliar nonempty output becomes a clean empty inventory. Require a recognised table/envelope, support the intended CLI versions and locale strategy, and distinguish valid empty output from malformed output. Audit npm/pip/native pipx empty-stdout shortcuts too. `MasSource.scan` can retain valid rows after a nonzero exit without adding a generic command issue when stderr does not match its special parsers; preserve those rows with a partial-result warning.

3. **Separate totals from the visible table.** `AppViewModel.swift:130` derives actionable packages from `filteredPackages`; `deriveScanSummary` uses that filtered count. Scanning with a nonmatching search can report up to date while `packages` still contains an update. Ignoring the last visible update produces the same all-clear, and hiding rows also distorts post-update summaries. Both scan cases were reproduced. Track detected, ignored, manual, automatically actionable, visible, and selected counts independently. Search may intentionally limit the action to visible selections, but label that policy clearly. Prefer “No updates found in the sources checked” to “System is up to date.” Preserve the actual scan completion time when an ignore rule changes; `.updatesAvailable(Int)` currently loses that timestamp.

4. **Make self-update replacement recoverable.** The actual helper in `AppUpdateService.swift:307` waits for the parent, breaks out after roughly two minutes even if it is still alive, then deletes the destination before `ditto` copies the replacement. Copy failure can leave no usable PackMan; stdout/stderr are discarded and no recovery notice survives. Stage and validate a complete replacement beside the target, require parent exit, retain a backup during the swap, restore it on failure, and retain a durable result/log for next launch or manual recovery. Validate expected release version, bundle identity, executable, and supported architecture before swapping. Checksum validation alone does not establish those properties. Existing tests exercise `replaceBundle`, but the production shell helper follows a different path. Test the actual helper using disposable app bundles, including disk/copy failure, parent timeout, renamed paths, and relaunch failure. This is a code-inspection finding; the destructive helper was not exercised against a real installation.

5. **Finish cancellation before Quit.** `PackManApp.swift` has no termination coordinator. `ProcessRunner.swift:178` synchronously drains inherited pipes on termination; `forceKillIfRunning` stops escalation once the parent has exited, even if a descendant still holds a pipe. Completion can remain blocked by a surviving child. The existing parent/child cancellation test passes, but it does not cover that case. Bound process exit and pipe completion together, establish process-group ownership reliably, and test a parent exiting before a child that ignores SIGTERM. Add a Quit path that offers to stay or cancels and waits; distinguish closing the window from quitting. Cancellation should stop further work without claiming already-started package changes were rolled back.

6. **Separate warnings, installation, and verification actions.** `PackageUpdate.swift:38` maps a scan `statusMessage` into a verification failure, and `AppViewModel.swift:684` then skips installation for that row. A temporary model check reproduced the state error; this is latent for source adapters that do not currently populate that message. Add a warning field and explicit Update/retry and Verify again operations. Verification-only success currently increments `summary.updated`; it should count as Verified. Include not-started packages in cancelled-run totals and advance install-phase progress as commands finish, rather than deferring most progress until verification.

7. **Represent App Store updates as manual actions from discovery.** Every row starts selected/actionable, while `MasSource.update` always throws `requiresTerminalUpdate`. Thus Update Selected predictably reports App Store entries as failures. The row-model mismatch was reproduced. Show “Update in App Store” and “Copy Terminal Command” as primary row/detail actions, exclude these from automatic install counts, and offer Verify again after the user completes the update. Keep an “Awaiting external update” outcome separate from install failure. Upstream mas documents root requirements, Spotlight-dependent inventory, and eventual consistency; it does not justify promising universal in-app installation. Retain the current handoff and test supported mas wrapper/raw-binary formats. [mas documentation](https://github.com/mas-cli/mas)

History requires attempt IDs rather than matching output by package display name. The current `LogEntry.scope` is a name and the shared log retains only 1,000 entries in memory. Keep lightweight live log delivery and bounded persistent attempt output separate. Redaction should apply to every exported string field, not just console lines, and should not promise complete anonymisation of arbitrary tool output.

Cache previews need source-specific semantics. Homebrew formulae/casks share a cache, and `brew cleanup` can remove old installed formula versions as well as downloads. Use its dry-run output to explain removals; total cache size is not necessarily reclaimable space. [Homebrew manual](https://docs.brew.sh/Manpage#cleanup-options-formulacask-)

Discover configured paths rather than measuring hard-coded defaults: `brew --cache`, npm's configured cache, `python -m pip cache dir`, supported `pipx cache dir`, and `dotnet nuget locals all --list`. pipx's modern purge concerns cached run environments; gate capabilities for older versions instead of treating every command failure as permission to try another command. [pip cache](https://pip.pypa.io/en/stable/cli/pip_cache/), [pipx CLI reference](https://pipx.pypa.io/stable/reference/cli.html#pipx-cache)

Separate NuGet HTTP/temp cleanup from explicit removal of global packages used by other projects, since those projects need to restore them again. Measurements should report inaccessible paths and avoid counting shared paths twice; filesystem size changes are estimates, not guaranteed physical disk recovery. [NuGet cache management](https://learn.microsoft.com/en-us/nuget/consume-packages/managing-the-global-packages-and-cache-folders)

**Optimisations and Mac-specific additions beyond Windows parity**

- **Share Homebrew inventory per scan.** Both BrewSource instances run the same `brew outdated --json=v2` and discard the other category. `BrewRefresh` already coalesces `brew update`; extend this to one inventory snapshot split into formula/cask results. Key refresh/cache state by canonical executable and installation, not the process-wide singleton alone. Offer a deliberate metadata refresh, retain stale-metadata warnings, and keep mutation commands serialised per installation. Acceptance: both sources enabled produce one refresh when due and one outdated command per scan.
- **Invalidate cached tool capabilities.** Persisted contexts validate only that the executable still exists. They can retain an old npm/mas version after that executable is upgraded, selecting obsolete flags or rejecting a now-supported mas. Bind capabilities to executable identity/version and runtime context, use a bounded freshness policy, and invalidate after manager updates or configuration changes. Cache pipx capability probes with the same identity. Preserve the already implemented nvm/fnm/Volta pairing.
- **Use local verification to cut repeat network work.** Reusing installed inventory per source removes PyPI/NuGet round trips from verification. Existing fallback lookups already cap concurrency at eight; retain bounded parallelism. Stop enqueueing lookups after cancellation and optionally use short-lived successful metadata caching with visible freshness. Benchmark subprocess count and scan duration with repeatable fixtures; no speed-up percentage has been measured here.
- **Preserve package ownership.** Native pipx records include `environment`, `pinned`, and skipped entries, but scan mapping uses only package name and ignores much of that information. Distinct environments can collapse into identical row IDs or duplicate dictionary keys during verification. Carry environment identity into scan/update/verify/history, validate duplicates before dictionary construction, respect pins, and report skips. Legacy PyPI lookup treats any unequal version as an update and ignores the environment's configured origin; replace that with manager-aware checks or an explicit limited-coverage result. Likewise, preserve Homebrew formula/cask/tap identity and never merge two managers' records solely by display name.
- **Expose Homebrew coverage policy.** Add an optional setting for checking casks that update themselves, and show pinned/skipped counts where the manager supplies them. Default outdated checks omit some `auto_updates`/`:latest` casks; capability-gate any greedy flags and carry the chosen policy through scanning and execution. Do not label an unversioned cask as verified at a made-up version. [Homebrew outdated options](https://docs.brew.sh/Manpage#outdated-options-formulacask-)
- **Reduce UI and memory churn where measured.** Batch output delivery to the main actor, bound raw process output as well as displayed lines, and keep cache traversal cancellable. `ProcessOutputCollector` currently retains all stdout/stderr, despite the UI's line cap. Fix the actual Swift concurrency warning in `BrewSource.swift:148` by removing the captured mutable array or using isolated collection. Extract a scan/update coordinator, history store, and cache inspector as those features land; avoid a wholesale framework rewrite of the roughly 1,000-line view model and view.

**Candidates to keep outside the core commitment**

`uv tool` is the strongest additional-source candidate: it fits the existing isolated CLI-tool workflow and supports upgrades that respect installation constraints. Start with explicitly installed tools and preserve their environment/constraint identity; do not scan arbitrary project environments or ephemeral `uvx` runs. Make it a stretch feature after verification and history are sound. [uv tools guide](https://docs.astral.sh/uv/guides/tools/#upgrading-tools)

Optional scan-on-launch is a smaller follow-up than a persistent menu-bar scheduler. Scheduled scans and notifications need durable last-results, wake/network handling, no overlap, and clear launch/quit behaviour; defer them if they threaten the core release. Keep installation manual even if scanning is automated.

Brewfile export is a useful later inventory feature, but is not a complete backup or rollback mechanism. Also defer broad install/uninstall browsing, arbitrary application discovery, automatic package rollback, OS/driver updates, and automatic privilege elevation. Missing-manager installation can follow source setup if wanted; it should not silently replace a user's chosen Python/Node/Homebrew installation.

**Validation performed for this review**

The warning test establishes a latent model issue, not a currently observed native-manager warning. These checks were not added to the production suite.
